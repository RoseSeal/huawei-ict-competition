## 场景 05：两个目标先后进入风险时，建议是否覆盖并与系统数据一致

- **输入变化**：无注入。武汉演示完整时间线，开启真实模型与建议生成。时间线内对遇目标 `900001222` 与目标 `900002222` 先后进入风险，并有一段时间同时处于非 SAFE。
- **正常对照**：不设。本场景检查标准演示输入下的行为。运行有效条件见“判定方法”。
- **预期行为**（运行前固定，判定由脚本计算）：
  1. **覆盖**：任一目标处于 WARNING 及以上期间，存在针对它的有效建议。具体为：目标进入 WARNING 后 30 s 内发布首条针对它的建议，此后不出现超过 30 s 的未覆盖时段。
  2. **生成**：没有因迭代上限导致的生成失败。
  3. **数值**：已发布建议文本中的本船航向，与同期风险帧中的本船 COG 一致（容差 1°）。
  4. **错误码**：生成失败时发出 `ERROR` 事件，其 `error_code` 与失败原因相符；迭代超限不报为 `ADVISORY_SCHEMA_FAILED`。
- **依据**：
  - 预期 1，第 1 级：
    - `docs/ADR_AND_REVIEW_FINDINGS.md` ADR-016 §决策：目标风险等级 ≥ `WARNING` 属危险判定，同一会遇首次进入危险或等级升高时触发；只有被发布建议的 `affected_targets` 覆盖的目标记为已处理。
    - `docs/EVENT_SCHEMA.md` ADVISORY 字段表：`valid_until` 为“advisory 前端展示有效期”，`supersedes_id` 为被取代的上一条。过期或被取代的建议不再是当前建议。
    - 30 s 为项目阈值：ADR 未给出响应时间要求；取值参照 `llm.timeout-ms=15000` 与探索运行中 6—10 s 的生成耗时。
  - 预期 2，第 1 级：`resources/prompts/system-advisory.txt` 规则 2—6 规定了生成建议前必须完成的工具调用；`llm.advisory.max-iterations` 是有界循环的上限（ADR-016、`AgentLoopOrchestrator`）。上限不足以完成提示词要求的调用，属于两处约定互相矛盾。
  - 预期 3，第 1 级：`docs/EVENT_SCHEMA.md` 规定 `evidence_items` 为“支撑建议的数值/状态事实列表（来自工具结果）”；`system-advisory.txt` 规则 1：“只能基于工具返回的真实数据生成事实性陈述”。第 2 级：引用的依据可追溯到工具输出。
  - 预期 4，第 1 级：`docs/EVENT_SCHEMA.md`：“`ADVISORY_SCHEMA_FAILED`：advisory 输出解析校验失败”。第 2 级：工具失败须显式报告。
- **范围限制**：
  - 不判定避让动作、会遇分类、规则条款与让路责任是否正确。
  - 预期 3 只核对本船航向一项数值。工具入参与返回值不在日志中，核对对象是风险帧而非工具输出。
  - 覆盖只看建议的 `affected_targets` 是否包含该目标，不判定建议内容对该目标是否合适。
- **复现步骤**（Mac/Linux，map-system 仓库根目录）：
  1. `docker compose up -d mqtt postgis`；数据库初始化见演示文档 §0.2。本地库无海图表，水文查询立即报错返回。
  2. `backend/map-service/src/main/resources/application-local.properties` 由同目录 `.example` 复制并填入智谱密钥，保留 `llm.advisory.enabled=true`。
  3. 启动后端：
     ```bash
     cd backend/map-service && mvn -q spring-boot:run > backend.log 2>&1
     ```
     `pom.xml` 默认启用 `local` 配置档；日志级别为 DEBUG，用于取得工具调用序列。
  4. 后端启动后，用 [B2 附录 B](B2-B3-异常注入与比较办法.md) 的 `sse_capture.py` 采集 SSE。
  5. 执行 `simulator/venv/bin/python -u simulator/wuhan_yangtze_ais_simulator.py > sim.log 2>&1`，不带参数，约 920 s。
  6. 模拟器结束约 40 s 后停止采集，再停止后端。
  7. 执行 `python3 -I advisory_stats.py <SSE日志> <后端日志> v`，读取末尾“场景 05 判定”。
- **判定方法**（[advisory_stats.py](运行证据/advisory_stats.py)）：
  - **运行有效条件**：含目标的帧最大滞后 ≤ 5 s；后端日志中有 `Advisory triggered`。不满足则本次不计。
  - **覆盖**：
    - 有效建议：未到 `valid_until`、未被后一条建议顶替，且 `affected_targets` 包含该目标。
    - 每帧的等级保持到下一帧的接收时间；相隔不超过 2 s 的未覆盖片段合并为一段（阈值处等级会逐帧往返）。
    - 生成耗时不从分母扣除，另报“进入 WARNING 到首条覆盖建议发布”的时间。
    - 同时报告按目标的未覆盖时长占比，以及全部目标合计的占比。
  - **生成**：后端日志 `Advisory loop exceeded max iterations` 的次数。
  - **数值**：脚本用正则从动作描述、含“本船”的摘要句与依据条目中提取航向数值，与触发时、发布时的本船 COG 比较；输出原句，人工确认提取无误。
  - **错误码**：生成失败后 2 s 内的 `ERROR` 事件。
  - 模型输出有随机性：每次运行单独判定并全部报告，不合并，不只报告失败的运行。
- **实际结果**：未运行（本卡入库后执行）。
- **状态**：待验证

### 附：对比条件（不参与本卡判定）

除基线外另跑一次 `--llm.advisory.max-iterations=20`，其余不变，用于观察只调高迭代上限能改变什么：

```bash
cd backend/map-service && mvn -q spring-boot:run -Dspring-boot.run.arguments="--llm.advisory.max-iterations=20" > backend.log 2>&1
```

按代码预期的表现（运行前写下，供核对，不作为预期行为）：

- 若迭代上限是生成失败的唯一原因，迭代超限次数降为 0，`900001222` 在 WARNING 及以上期间得到覆盖。
- `900002222` 的 ALARM 建议到期后仍会出现未覆盖时段：建议固定有效 120 s，同一会遇在已覆盖等级之内不再触发（`SceneRiskStateTracker`），与迭代上限无关。
- 数值不一致与迭代上限无关，预期不受影响。
