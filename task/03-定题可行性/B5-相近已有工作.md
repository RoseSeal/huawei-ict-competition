# B5：相近已有工作做到了什么？

> 按[任务表](README.md) B5 条目整理：VaMAI-Validator、SceneGEMS 相关研究、MAEI-2D 各自测什么、用什么方法、是否开源，以及与拟议能力（[方向分析](../../research/03-候选方向/方向分析-2026-10-29.md) §6「航行 AI 测试与失效诊断平台」）的异同。
> 三项均按原文整理：VaMAI-Validator 取自 ICAS26 论文 PDF 全文（已下载提取，见[运行证据](运行证据/ICAS26_20005.pdf)）；S5 取自作者说明页与两个代码仓库；S6 取自 MDPI 论文页（本轮已取得正文）。整理日期 2026-11-09。

## 结论（TL;DR）

**三项相近工作均没有做到拟议能力的核心组合**：对真实被测系统运行「任务语义 + 运行反馈引导的失效搜索 → 失败用例缩减 → 经对照实验复查的失效诊断」。具体到能力维度：

| 能力维度（§6.3） | VaMAI-Validator | SceneGEMS / MSR（S5） | MAEI-2D（S6） |
|---|---|---|---|
| 测试条件理解 | 场景/指标/规则由人工准备 | 场景规格由 Refinery 语法编写或选预设 | LLM 将测试需求转成 7 字段测试方案 |
| 失败搜索 | 无（人工场景） | 有，但为约束求解/采样（非运行反馈引导），保证场景级覆盖 | 无（评估方案质量，不搜索被测系统失效） |
| 失败用例缩减 | 无 | 无（场景按 FEC 枚举生成，不缩减） | 无 |
| 失效诊断 | 反馈"检出行为缺陷"，无假设检验 | monitor 输出违规证据，无根因假设 | 评估报告，无被测系统失效诊断 |
| 是否开源 | ❌ 未定（"Open-source status undecided"） | ✅ MIT（MSR 仓库 + SceneGEMS monorepo + Zenodo 工件） | ❌（无代码链接，数据不公开） |

方向分析 §6.4 将 MAEI-2D 列为"相近工作线索，具体方法与适用任务仍待全文核查"——本轮已完成核查，边界判断（"证据不足以支持'首次用 LLM 生成海事场景'或'海事 AI 没有测试框架'"）成立且更具体了。

## 1. VaMAI-Validator（ICAS26 论文，德国 ATB 研究所）

**来源**：[ICAS26 20005 PDF](https://www.iaria.org/conferences2026/filesICAS26/20005_ICAS.pdf)（overview.md 依据条目引用；本轮下载 PDF 提取全文，12 页为演示文稿体例）。作者 Christoph Baier 等，Institute for Applied Systems Technology Bremen（ATB），EU 项目资助。

**测什么**：自主船舶航行 Agent（"Agents – algorithm controlling the autonomous vessel"）的验证平台。三要素插件化：Scenarios（导航任务：vessels、targets、obstacles）、Metrics（如 collision risk index）、Rules（如 COLREG、good seamanship）。针对的问题（原文"Addressed Issues"）：自主航行验证复杂、仿真开发成本高、Agent 工具碎片化、缺自动验证、跨 Agent 重复实现。

**用什么方法**：测试驱动开发式工作流——"1. Prepare scenarios, metrics, rules → 2. Write agent code → 3. Run validation → 4. Analyze feedback → 5. If performance gets worse, then rollback, otherwise continue"。方法验证两部分：① 仿真精度对照：无人艇与有人会遇船实艇试验，静风条件下虚拟仿真"about 1.5 m average position deviation"；② 案例研究：对原型导航 Agent "Pathplanner" 做验证（插件为基本航行/避障与 2 船 COLREG 会遇场景、基于 DCPA/TCPA 的 CRI 指标、简化 COLREG 规则），"Result: Detection of behavioral flaws"。

**是否开源**：**否**。结论页原文："Open-source status undecided / Direction depends on feedback / Contact us for software access or cooperation"。

**局限（作者自述）**：环境假设简化（缺环境因素、船体几何抽象）、插件简单、仅 C++ 客户端接口、Agent 集成数 n=2、通用性主张需进一步验证。

**与拟议能力的异同**：
- 同：同样面向航行 Agent 的仿真验证、同样抽象出场景/指标/规则三要素并强调跨 Agent 复用；其"测试平台本身不构成首创依据"的定位已在 [overview.md](../../overview.md) 记录。
- 异：VaMAI 的场景是**人工准备**的固定集合，无失效搜索、无用例缩减、无 AI 诊断；其反馈是指标/规则检查结果，不形成"原因假设 + 对照实验"的闭环。它证明"航行 Agent 验证平台"已存在，但不覆盖拟议能力中"数据时效、信息到达顺序、Agent 工具行为共同导致的失效"这一搜索与诊断主张。

## 2. SceneGEMS 相关研究（S5：MODELS 2026 论文 + MSR 仓库 + SceneGEMS 框架）

**来源**：[作者说明页](https://dominikfrey.dev/a/models-2026-functionally-complete-assurance-suites)、[MSR 仓库](https://github.com/PELAB-LiU/MSR_ASV_SceneGeneration)、[SceneGEMS 页](https://dominikfrey.dev/a/scenegems)。论文：Frey, Kargén, Varró, "Automated Generation of Functionally Complete Assurance Suites for COLREGS-Compliance of Autonomous Surface Vehicles", ACM/IEEE MODELS 2026, pp.293–304（Linköping University PELAB）。

**测什么**：ASV 的 COLREG 合规性场景级保证——回答"system-level tests 中 which scenarios to run"：历史流量与随机生成器会漏掉罕见临界边例，无法提供"每一类相关会遇都被测过"的语义保证（其 ISSTA 2025 研究实证了这一点）。覆盖 2–6 船会遇。

**用什么方法**：多步细化 MSR（multi-step refinement）三步——① 枚举：Refinery 图求解器列出符合 COLREG 元模型的**每个功能等价类 FEC**（每类对应不同 COLREG 规则适用）；② 映射：每类抽象关系转为 COLREG 专属几何约束（能见距离 6 NM、碰撞航向、扇区归属等）；③ 具体化：增强拒绝采样在约束交集内用 Scenic 采样，导出具体初始场景。基线为 direct concretisation（NSGA-II/III 或纯拒绝采样，同全局超时）。**结果：2–6 船 100% FEC 覆盖**，MSR 的覆盖-时间曲线优于直接具体化，增强拒绝采样扩展性最好。

**是否开源**：**是，且工件完备**。
- MSR 仓库 github.com/PELAB-LiU/MSR_ASV_SceneGeneration：MIT，Python，MODELS26 artifact evaluation 包，Streamlit 演示器 + Docker；Zenodo 软件工件 10.5281/zenodo.19246756（v5.0，MIT）、测量数据 10.5281/zenodo.20792733/20792734（CC-BY 4.0）。
- SceneGEMS monorepo（github.com/fdominik98/SceneGEMS）：MIT，Python，2026-07 创建、2026-11-05 仍在推送。端到端："specification → scene generation → simulation → compliance monitoring"；组件含 Python WebSocket 后端、React 控制台、三级场景管线、Gazebo Harmonic + ArduPilot SITL 仿真镜像、运行时 COLREG monitor（"assesses safety and COLREGS compliance"并"exported as assurance evidence"），Docker + MQTT 编排，与 WARA-PS 核心系统集成（每船独立 MQTT 主题），支持软件在环与真实/仿真混合。

**与拟议能力的异同**：
- 同：同属"海事情景生成 + 仿真评测"域；同样把场景抽象分层（functional/logical/concrete ↔ 拟议的"要求转成可审查的判定条件"）；SceneGEMS 已打通"生成→仿真→监控→证据导出"链路，且 MQTT 集成方式与 B2 的 `usv/AisMessage` 主题模型同构（也是上一任务 B4 调研之外一个值得注意的潜在第二被测对象/对照底座，见 `Desktop/航船/04-被测对象调研/开源被测对象调研.md`）。
- 异（关键）：其"完备性"是**场景几何类的完备**，保证对象是 COLREG 合规，不是被测 Agent 的失效；其搜索是约束求解与采样（由 FEC 语义驱动，但**不由被测系统的运行反馈引导**）；不针对数据时效/工具契约/模型响应类失效；无失败用例缩减；monitor 产出违规证据而非经对照实验复查的根因诊断。方向分析 §6.4 要求核验的差异——"船舶状态变化、信息到达顺序和 Agent 工具行为共同导致的失效，是否能够被统一搜索、缩减，并形成可用于修复的实验材料"——**在 SceneGEMS/MSR 中确实没有做到**。

## 3. MAEI-2D（S6：Applied Sciences 2026 论文，北航等）

**来源**：[MDPI 论文页](https://www.mdpi.com/2076-3417/16/12/6229)，Ren, Ma, Yu, Li, Dong, Zhang，"A Multi-Agent Model for Automatic Test Scheme Generation via Experience Interaction and 2D-Simulation Evaluation"，Applied Sciences 2026, 16(12), 6229（2026-06-20 出版）。方向分析 §6.4 记录当时"后续直接打开遇访问限制，未完成全文方法审查"——本轮已取得正文。

**测什么**：海事装备（USV、UUV、智能仿生设备）的智能水平与协同能力测试——自动生成标准化**测试方案**（七字段：Mission、Subjects、Resources、Environment、Rules、Procedure、Time Axis）。实验示例为 USV 平台"水面移动目标跟踪"测试方案生成。注意：它测的是**测试方案本身的质量**，不是对真实被测系统注入失效。

**用什么方法**：LLM 多 Agent 闭环 Generator → Simulator → Evaluator（LLM 为 DeepSeek-r1_70b）：① 经验交互——Generator 用混合检索（稀疏词法匹配 + 字段级语义相似度重排，评分公式 S(Q,Hi)=α·sim(Q,Hi)+(1−α)·max_f(s_f(Q,Hi))）从历史海军测试方案与专家案例库 RAG 复用经验；② 2D 仿真评估——二维网格海洋环境离散推演，LLM 驱动 Orchestrator 与 ScenarioBuilder 交互，输出逐步执行报告 {r_t}；③ 四维评估——Difficulty/Economy 由统计规则计算，Feasibility/Efficiency 由 LLM 生成式评估执行报告，反馈驱动 Generator 迭代（≤3 次）。**实验**：与 MAEI-SA（仅生成 Agent）和直接 LLM 生成对比，各 100 个方案；指标 EES（经济性）、可行性（缺失/异常字段数）、Cov/Pre（5 位专家标注，Fleiss' kappa>0.8）；消融显示去掉 simulator 或 evaluator 均下降；结论"our approach outperforms the method based on LLMs directly"。

**是否开源**：**否**。无代码仓库链接；数据可用性声明原文："The datasets presented in this article are not publicly available due to privacy restrictions. Requests to access the datasets should be directed to the corresponding author."

**局限（作者自述）**：依赖大模型推理能力，幻觉风险影响生成结果；评估是任务特定的（"its evaluation is task-specific... The results are preliminary and require more rigorous validation"）。

**与拟议能力的异同**：
- 同：这是三项中与拟议能力**方法形态最接近**的一项——同样用 LLM 把任务语义转成可执行测试材料、同样以"完整方法 vs 消融 vs 直接 LLM"的比较设计支撑 AI 增量主张（与方向分析 §6.5 的消融约束同构，可作为拟议评价设计的直接参照）；也共享"程序负责可计算部分、LLM 负责语义部分"的分工思路。
- 异：MAEI-2D 的产物是**测试方案文档**（去野外执行的海事试验方案），2D 网格仿真评估的是方案可行/经济/难度，而非对真实软件系统运行失效搜索；没有"在运行反馈引导下变换输入组合寻找违反要求"的环节；无失败缩减与根因诊断；面向试验任务规划领域，不是软件在环测试。

## 4. 对方向分析边界判断的影响

§6.4 的两句判断本轮均可落实：

1. "海事情景生成、搜索式测试、仿真评测及 Agent 测试均已有工作"——**成立**：场景生成端 SceneGEMS/MSR 已做到功能完备覆盖并端到端开源；Agent 验证平台 VaMAI-Validator 已有平台化先例；LLM 多 Agent 测试生成 MAEI-2D 已发表并给出消融证据。拟议能力的创新主张不能落在"平台本身"或"LLM 生成海事场景"上，与 overview.md 既有记录一致。
2. 拟议能力的差异化空间**收窄为三点**，且三项相近工作均未覆盖：
   - 失效类型：数据时效、信息到达顺序、Agent 工具行为共同导致的软件链路失效（我们已用 3 张失败场景卡实证 B2 在此类型上的真实缺陷）；
   - 搜索机制：任务语义 + **运行反馈**引导的失效搜索（SceneGEMS 的语义引导止步于场景枚举，不消费被测系统运行结果）；
   - 后处理闭环：失败用例缩减 + 假设-对照式失效诊断 + 版本回归比较。
   同时，MAEI-2D 的消融式评价设计（完整方法/去组件/直接 LLM、同预算、专家标注）可直接借用为 §6.5"AI 增量"评价的参照实现。
